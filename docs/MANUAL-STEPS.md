> لم يُنفَّذ أي شيء من هذه الخطوات تلقائياً. لا SQL على قاعدة الإنتاج، ولا نشر، ولا تغيير على Render/Firebase/GitHub.
> الترتيب مهم: **(1) الترحيلات → (2) متغيرات Render → (3) نشر الخادم → (4) إصدار التطبيق**.

## 1) ترحيلات Supabase (بالترتيب، كلها آمنة للتكرار)

شغّلها من Supabase SQL Editor (أو `supabase db push` بعد مراجعتها) خارج وقت الذروة:

| # | الملف | ما يفعله | ما يتعطل قبله |
|---|---|---|---|
| 0 | `20261108100000_account_deletion_email_codes.sql` | جدول رموز حذف الحساب (كان غير مطبّق في الإنتاج) | إرسال رمز حذف الحساب يعطي 503 |
| 1 | `20261114100000_auth_rate_limits.sql` | عدّاد حدود المحاولات المشترك (جدول + دوال) | تعمل الحدود بعدّاد داخل كل نسخة خادم فقط (مع تحذير في السجل) |
| 2 | `20261114100100_registration_otp_codes.sql` | رموز التسجيل المخزَّنة (استخدام واحد) | لا شيء ما دام `REGISTRATION_OTP_ENABLED=false` |
| 3 | `20261114100200_session_revocation_and_admin_2fa.sql` | `users.token_version` + أعمدة 2FA + أكواد الاسترداد | لا يعمل «تسجيل الخروج من كل الأجهزة»، ولا إبطال الجلسات عند تغيير كلمة المرور، ولا 2FA |
| 4 | `20261114100300_receipt_fingerprints.sql` | منع إعادة استخدام إيصال الدفع + قفل عند الموافقة | تبقى الطلبات تعمل لكن بلا منع لتكرار الإيصال (تحذير في السجل) |
| 5 | `20261114100400_referral_tracking.sql` | تسجيل الإحالات وأعلام الأنماط المشبوهة | لا تُسجَّل أعلام (التسجيل نفسه يعمل) |
| 6 | `20261114100500_data_integrity_constraints.sql` | قيود CHECK (غير سالبة)، فهرس فريد لعمولة لكل طلب، `debt_ledger.created_by`، حدود bucket `euro_uploads` | لا شيء |

ملاحظات:
- القيود تُضاف `NOT VALID` ثم يُحاوَل التحقق منها؛ إذا خالفتها بيانات قديمة تظهر رسالة `NOTICE` ولا يفشل الترحيل.
- الفهرس الفريد على `marketer_commissions(order_id)` يُتخطّى برسالة `NOTICE` إذا وُجد تكرار قديم (راجعه أولاً).
- اختياري: جدولة تنظيف دوري (pg_cron): `select public.auth_rate_cleanup();` و`select public.registration_otp_cleanup();`
- تحقق بعد التطبيق (قراءة فقط): `select count(*) from public.auth_rate_limits;` و`select column_name from information_schema.columns where table_name='users' and column_name in ('token_version','totp_enabled_at');`

## 2) متغيرات Render (الخدمة `al-euro` فقط)

| المتغير | القيمة | متى |
|---|---|---|
| `TOTP_ENC_KEY` | قيمة عشوائية: `openssl rand -base64 32` | قبل تفعيل 2FA لأي أدمن (يشفّر أسرار التطبيق) |
| `OTP_DAILY_CAP` | اختياري (الافتراضي 500 رسالة/يوم) | حسب ميزانية واتساب |
| `REGISTRATION_OTP_ENABLED` | اتركه `false` حالياً | غيّره إلى `true` فقط بعد تطبيق الترحيل 2 واختبار Green API |
| `ADMIN_2FA_DISABLED` | لا تضبطه | طوارئ فقط (ضياع هاتف الأدمن)، واحذفه بعد الاستخدام |

لا تغيّر `AUTH_SECRET` (تغييره يسجّل الجميع خروجاً ويقفل أسرار 2FA إذا لم يُضبط `TOTP_ENC_KEY`).

## 3) النشر والتوافق

- الجلسات الحالية تبقى صالحة بعد النشر (التوكن بلا إصدار = إصدار 0).
- بعد **تغيير كلمة المرور/رقم الهاتف** يُبطَل كل توكن قديم ويستلم الجهاز الحالي توكن جديداً (`accessToken`). نسخ التطبيق القديمة لا تتبنّى التوكن الجديد، فيُطلب منها تسجيل الدخول مرة واحدة بعد التغيير؛ النسخة الجديدة تتبنّاه تلقائياً.
- الدخول القديم بكلمات مرور من 4 أحرف ما زال يعمل. الحد الأدنى 8 أحرف لكلمات المرور **الجديدة** فقط (تسجيل، تغيير، استعادة).
- رسالة الدخول الخاطئ موحّدة (401) ولم يعد 404 «لا يوجد حساب».
- بعد 5 محاولات دخول خاطئة للحساب نفسه: حظر 15 دقيقة (429). ملاحظة: شبكات الجوال المشتركة (CGNAT) تُحسب بالعنوان، فحدّ العنوان الواحد 30 محاولة فاشلة/10 دقائق.

## 4) التحقق بخطوتين للأدمن (F-03)

1. اضبط `TOTP_ENC_KEY` ثم انشر وطبّق الترحيل 3.
2. ادخل لوحة الإدارة ← «الأمان» ← «بدء الإعداد»، أضف المفتاح لتطبيق مصادقة، أدخل الرمز، **احفظ رموز الاسترداد الثمانية** (تظهر مرة واحدة).
3. لا يُفرض على أي أدمن قبل أن يُنهي إعداده بنفسه. للإيقاف: من نفس الصفحة (كلمة المرور + رمز).
4. ضياع الهاتف: استخدم رمز استرداد (استخدام واحد)، أو الطوارئ `ADMIN_2FA_DISABLED=true` مؤقتاً.

## 5) Firebase App Check (F-13) — مراقبة فقط

1. Firebase Console ← App Check ← سجّل تطبيق Android بمزوّد **Play Integrity** (يتطلب ربط المشروع بـ Play Console وإضافة بصمة SHA-256 لمفتاح التوقيع).
2. للاختبار على جهاز تطوير: فعّل Debug provider وأضف الـ debug token الذي يطبعه التطبيق.
3. **لا تضغط Enforce** على Authentication أو Cloud Messaging قبل أن تُظهر مقاييس الـ Console أن معظم الطلبات «Verified». التطبيق لا يرسل توكنات App Check لخادم EURO.
4. نسخة iOS: عند إضافتها فعّل DeviceCheck/App Attest بالمثل.

## 6) GitHub

- ثبّت الـ Actions على commit SHA: شغّل `scripts/pin-actions.sh` (يستخدم `gh` عندك) في كل مستودع ثم راجع الفرق. لم أتمكن من حلّ الـ SHA من هنا فلم أضع قيماً مخمّنة.
- فعّل: Secret scanning + Push protection، Dependabot alerts، وحماية فرع `main` (مراجعة + نجاح الفحوص).
- أنشئ ملفات القفل ثم ارفعها: `npm install --package-lock-only` في `al-euro` و`al-euro-referrals`، و`flutter pub get` ثم ارفع `pubspec.lock`.
- سير عمل APK: صار `contents: write` في مهمة `publish` فقط (بعد نجاح البناء). لم يُشغَّل بعد؛ راقب أول تشغيل.

## 7) خدمة الإحالات `al-euro-referrals` (F-12)

- رُفع Next إلى 15.5.29 وأُضيفت ترويسات أمان (CSP، منع الإطار، no-referrer، HSTS) وشعار محلي. أعد النشر على Render بعد `npm install`، وجرّب `/r?ref=MK-XXXXXX&sig=...` على جهاز فعلي.
- لم أتمكن من بناء الخدمة هنا (لا شبكة لحزم npm).
